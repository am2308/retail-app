Phase 1

VNet Peering — connecting two private networks

In Session 1 you created one VNet. Real companies have many — one per team, one per environment. VNet Peering connects them privately over Microsoft's backbone. Zero internet, zero VPN, sub-millisecond latency.

Why Peering

VNet Peering vs the alternatives

🔗
VNet Peering
Microsoft backbone, no public internet, no gateway needed, sub-ms latency, pay per GB transferred. Use this for same-region or cross-region private connectivity.
🛡️
VPN Gateway
Encrypted tunnel, works for on-premises connectivity. Higher latency (~10–50ms), costs ~$130+/month for the gateway. Use for on-prem, not VNet-to-VNet.
🌐
ExpressRoute
Private dedicated circuit from on-prem to Azure. Extremely reliable, very expensive. Enterprise on-prem connectivity only — not for VNet-to-VNet.
Key facts about VNet Peering: It is non-transitive — if VNet-A peers with VNet-B, and VNet-B peers with VNet-C, VNet-A cannot reach VNet-C. You need a hub-spoke topology with Azure Firewall or Virtual WAN for transitive routing. Peering is directional — you create TWO peerings (A→B and B→A).

CLI — Same result, scriptable

VNet Peering from az cli

Terminal — create both VNets and peer thembash
# ── Variables ─────────────────────────────────────────────────────────────────
RG_DEV="rg-dev"
RG_PAY="rg-payments-prod"
LOCATION="westeurope"
VNET_DEV="vnet-dev"
VNET_PAY="vnet-payments"

# ── Create resource groups (if not already done) ─────────────────────────────
az group create --name $RG_DEV  --location $LOCATION
az group create --name $RG_PAY --location $LOCATION

# ── Create VNet-Dev ──────────────────────────────────────────────────────────
az network vnet create \
  --name $VNET_DEV \
  --resource-group $RG_DEV \
  --address-prefix 10.1.0.0/16 \
  --subnet-name snet-dev-app \
  --subnet-prefix 10.1.1.0/24

# ── Create VNet-Payments ─────────────────────────────────────────────────────
az network vnet create \
  --name $VNET_PAY \
  --resource-group $RG_PAY \
  --address-prefix 10.2.0.0/16 \
  --subnet-name snet-payments-app \
  --subnet-prefix 10.2.1.0/24

# ── Get VNet resource IDs (needed for cross-RG peering) ──────────────────────
VNET_DEV_ID=$(az network vnet show \
  --name $VNET_DEV --resource-group $RG_DEV \
  --query id --output tsv)

VNET_PAY_ID=$(az network vnet show \
  --name $VNET_PAY --resource-group $RG_PAY \
  --query id --output tsv)

echo "Dev VNet ID:      $VNET_DEV_ID"
echo "Payments VNet ID: $VNET_PAY_ID"

# ── Create peering A → B (Dev → Payments) ────────────────────────────────────
az network vnet peering create \
  --name peer-dev-to-payments \
  --resource-group $RG_DEV \
  --vnet-name $VNET_DEV \
  --remote-vnet $VNET_PAY_ID \
  --allow-vnet-access true \
  --allow-forwarded-traffic true

# ── Create peering B → A (Payments → Dev) ────────────────────────────────────
# Both directions MUST be created — peering is not automatic both ways
az network vnet peering create \
  --name peer-payments-to-dev \
  --resource-group $RG_PAY \
  --vnet-name $VNET_PAY \
  --remote-vnet $VNET_DEV_ID \
  --allow-vnet-access true \
  --allow-forwarded-traffic true

# ── Verify both peerings are Connected ───────────────────────────────────────
az network vnet peering list \
  --resource-group $RG_DEV \
  --vnet-name $VNET_DEV \
  --query "[].{Name:name, State:peeringState, Remote:remoteVirtualNetwork.id}" \
  --output table

# Expected:
# Name                  State      Remote
# peer-dev-to-payments  Connected  /subscriptions/.../vnet-payments

# ── Test connectivity: SSH into VM in VNet-Dev, ping VM in VNet-Payments ─────
# (both VMs must exist and NSGs must allow ICMP)
ssh -i ~/.ssh/northbank-vm-key azureuser@<vm-dev-private-ip>
ping 10.2.1.4   # private IP of VM in payments subnet — should reply
Phase 2

Azure Bastion — SSH without exposing VMs to the internet

In Session 1 your mentee SSH'd via a public IP on the VM. That public IP is a direct attack surface — bots scan it constantly. Azure Bastion provides browser-based SSH and RDP through the Azure Portal with no public IP on the VM at all.

✗Session 1 approach — public IP SSH
✗
VM has a public IP — directly reachable from anywhere on internet. Bots scan port 22 continuously.
✗
NSG must allow port 22 from internet — even with source IP restriction, it's an exposed attack surface.
✗
Private key must be on laptop — if laptop is lost or key is leaked, attacker has VM access.
✓Azure Bastion — what changes
✓
VM has NO public IP — completely invisible from internet. Cannot be port-scanned.
✓
NSG has no port 22 rule — Bastion communicates to VM on port 22 internally from its dedicated subnet.
✓
SSH via browser — Azure Portal → VM → Connect → Bastion. Auth uses Azure AD or SSH key stored in Key Vault.
✓
Session logs — every Bastion session is logged in Azure Monitor. Full audit trail of who accessed what VM when.
Architecture

How Bastion works — what the mandatory subnet is for

Bastion sits in its own dedicated subnet inside YOUR VNet
Your Browser

→
Azure Bastion
AzureBastionSubnet /26 min
→ port 22/3389 →
payment-api-vm

The subnet name MUST be exactly AzureBastionSubnet — Azure looks for this specific name. Any other name and deployment fails. Minimum size is /26 (64 IPs). Reserve this in your VNet address plan from the start.

CLI

Deploy Bastion from az cli

Terminal — create Bastion subnet, public IP, and Bastion hostbash
RG="rg-payments-prod"
VNET="vnet-payments"
VM_NAME="payment-api-vm"
LOCATION="westeurope"

# ── Step 1: Add the mandatory AzureBastionSubnet ──────────────────────────────
# Name is hardcoded — Azure checks for this exact string
az network vnet subnet create \
  --resource-group $RG \
  --vnet-name $VNET \
  --name AzureBastionSubnet \
  --address-prefix 10.2.255.0/26

# ── Step 2: Create a public IP for Bastion (Standard SKU required) ────────────
az network public-ip create \
  --resource-group $RG \
  --name pip-bastion-payments \
  --sku Standard \
  --allocation-method Static \
  --location $LOCATION

# ── Step 3: Deploy the Bastion host ──────────────────────────────────────────
# Takes 5-10 min — Bastion spins up managed infrastructure inside your subnet
az network bastion create \
  --resource-group $RG \
  --name bastion-payments \
  --vnet-name $VNET \
  --public-ip-address pip-bastion-payments \
  --location $LOCATION \
  --sku Basic

# ── Step 4: Remove public IP from the VM (make it private-only) ──────────────
NIC_NAME=$(az vm show \
  --resource-group $RG --name $VM_NAME \
  --query "networkProfile.networkInterfaces[0].id" \
  --output tsv | xargs basename)

az network nic ip-config update \
  --resource-group $RG \
  --nic-name $NIC_NAME \
  --name ipconfig1 \
  --remove publicIpAddress

# Verify the VM has no public IP now
az vm list-ip-addresses \
  --resource-group $RG \
  --name $VM_NAME \
  --output table
# PublicIpAddresses column should be empty

# ── Step 5: SSH via Bastion from CLI (az network bastion ssh) ─────────────────
# This opens an SSH session through Bastion from your terminal — no browser needed
az network bastion ssh \
  --resource-group $RG \
  --name bastion-payments \
  --target-resource-id $(az vm show --resource-group $RG --name $VM_NAME --query id --output tsv) \
  --auth-type ssh-key \
  --username azureuser \
  --ssh-key ~/.ssh/northbank-vm-key.pem

# You're inside the VM — no public IP, no direct port 22 exposure
Phase 3

Azure Firewall + UDR — inspect and control all traffic

NSGs (from Session 1) filter traffic at the NIC and subnet level. Azure Firewall is a managed, stateful network firewall that sits at the VNet edge, inspects all traffic, logs everything, and can do FQDN filtering — block *.evil.com while allowing *.microsoft.com.

FeatureNSG (Session 1)Azure Firewall
LayerL4 — IP/portL4 + L7 — FQDN, HTTP headers
ScopeSubnet or NICEntire VNet / hub
FQDN filtering✗✓ Allow *.microsoft.com, deny rest
Threat intelligence✗✓ Blocks known malicious IPs/domains
Centralised loggingFlow logs only✓ Every allow/deny logged to Log Analytics
CostFree~$1.25/hr + $0.016/GB processed
Use both?Yes — NSG for micro-segmentation, Firewall for edge control. They complement each other.
UDR (User Defined Route) is what forces traffic through Firewall. Without a UDR, VM traffic goes directly to its destination — bypassing Firewall completely. The UDR says: "default route (0.0.0.0/0) → next hop = Firewall private IP". Every packet leaving the subnet goes through Firewall first.
Portal

Deploy Azure Firewall from Portal

Create AzureFirewallSubnet in your VNet

Go to vnet-payments → Subnets → + Subnet. Name: AzureFirewallSubnet (exact spelling). Address: 10.2.254.0/26. Save. Like Bastion, the subnet name is hardcoded — Azure refuses to deploy Firewall to any other name.

vnet-payments → Subnets → + Subnet → AzureFirewallSubnet → 10.2.254.0/26

Create Firewall Policy first

Search Firewall Policies → + Create. Name: policy-northbank. Region: same as VNet. Tier: Standard. Create. The policy is a container for all your rules — you attach it to the Firewall, not define rules directly on the Firewall.

Firewall Policies → + Create → policy-northbank → Standard → Create

Create Azure Firewall

Search Firewalls → + Create. Resource group: rg-payments-prod. Name: fw-northbank. Region: match VNet. Tier: Standard. Firewall management: Use a Firewall Policy → select policy-northbank. VNet: vnet-payments. Public IP: Create new → pip-fw-northbank. Review + Create (takes ~10 min).

Firewalls → + Create → fw-northbank → Standard → Policy: policy-northbank → VNet: vnet-payments

Get Firewall private IP — you need this for the UDR

Once deployed, go to fw-northbank → Overview. Note the Private IP address (e.g. 10.2.254.4). This is what the route table will point to.

fw-northbank → Overview → Private IP address: 10.2.254.4 (copy this)

Create a Route Table (UDR) and add default route

Search Route tables → + Create. Resource group: rg-payments-prod. Name: rt-payments-app. Region: match VNet. Propagate gateway routes: No. Create. Then go to the route table → Routes → + Add. Route name: default-to-firewall. Destination: 0.0.0.0/0. Next hop: Virtual appliance. Next hop address: 10.2.254.4 (Firewall private IP). Add.

Route tables → + Create → rt-payments-app → Routes → + Add → 0.0.0.0/0 → Virtual appliance → 10.2.254.4

Associate Route Table with the app subnet

In the route table → Subnets → + Associate. VNet: vnet-payments. Subnet: snet-payments-app. Associate. All traffic from VMs in this subnet now routes through Firewall first.

rt-payments-app → Subnets → + Associate → vnet-payments → snet-payments-app
Terminal — full Azure Firewall + UDR setupbash
RG="rg-payments-prod"
VNET="vnet-payments"
LOCATION="westeurope"
FW_NAME="fw-northbank"

# ── Step 1: Create AzureFirewallSubnet ───────────────────────────────────────
az network vnet subnet create \
  --resource-group $RG \
  --vnet-name $VNET \
  --name AzureFirewallSubnet \
  --address-prefix 10.2.254.0/26

# ── Step 2: Create public IP for Firewall ─────────────────────────────────────
az network public-ip create \
  --resource-group $RG \
  --name pip-fw-northbank \
  --sku Standard \
  --allocation-method Static

# ── Step 3: Create Firewall Policy ───────────────────────────────────────────
az network firewall policy create \
  --resource-group $RG \
  --name policy-northbank \
  --location $LOCATION \
  --sku Standard \
  --threat-intel-mode Alert   # Alert on known malicious IPs/domains

# ── Step 4: Create Azure Firewall ────────────────────────────────────────────
# Takes ~10 min
az network firewall create \
  --resource-group $RG \
  --name $FW_NAME \
  --location $LOCATION \
  --sku AZFW_VNet \
  --tier Standard \
  --firewall-policy policy-northbank \
  --vnet-name $VNET \
  --public-ip pip-fw-northbank

# ── Step 5: Get the Firewall private IP ──────────────────────────────────────
FW_PRIVATE_IP=$(az network firewall show \
  --resource-group $RG \
  --name $FW_NAME \
  --query "ipConfigurations[0].privateIPAddress" \
  --output tsv)
echo "Firewall Private IP: $FW_PRIVATE_IP"

# ── Step 6: Create Route Table ───────────────────────────────────────────────
az network route-table create \
  --resource-group $RG \
  --name rt-payments-app \
  --location $LOCATION \
  --disable-bgp-route-propagation true

# ── Step 7: Add default route → Firewall ─────────────────────────────────────
az network route-table route create \
  --resource-group $RG \
  --route-table-name rt-payments-app \
  --name default-to-firewall \
  --address-prefix 0.0.0.0/0 \
  --next-hop-type VirtualAppliance \
  --next-hop-ip-address $FW_PRIVATE_IP

# ── Step 8: Associate route table with app subnet ────────────────────────────
az network vnet subnet update \
  --resource-group $RG \
  --vnet-name $VNET \
  --name snet-payments-app \
  --route-table rt-payments-app

echo "UDR applied — all traffic from snet-payments-app now routes through Firewall"
Terminal — add Firewall rules: allow specific, deny restbash
RG="rg-payments-prod"
POLICY="policy-northbank"

# ── Rule Collection Group (logical grouping for rules) ───────────────────────
az network firewall policy rule-collection-group create \
  --resource-group $RG \
  --policy-name $POLICY \
  --name "northbank-rules" \
  --priority 100

# ── Application Rule: allow outbound HTTPS to Microsoft services only ─────────
# VMs can reach *.microsoft.com and *.azure.com — nothing else on HTTPS
az network firewall policy rule-collection-group collection add-filter-collection \
  --resource-group $RG \
  --policy-name $POLICY \
  --rule-collection-group-name "northbank-rules" \
  --name "allow-microsoft-https" \
  --collection-priority 100 \
  --action Allow \
  --rule-name "allow-microsoft" \
  --rule-type ApplicationRule \
  --protocols "Https=443" \
  --fqdn-tags MicrosoftActiveProtectionService WindowsUpdate \
  --target-fqdns "*.microsoft.com" "*.azure.com" "*.windows.net" \
  --source-addresses "10.2.0.0/16"

# ── Network Rule: allow DNS (without this, nothing resolves) ─────────────────
az network firewall policy rule-collection-group collection add-filter-collection \
  --resource-group $RG \
  --policy-name $POLICY \
  --rule-collection-group-name "northbank-rules" \
  --name "allow-dns" \
  --collection-priority 200 \
  --action Allow \
  --rule-name "allow-udp-dns" \
  --rule-type NetworkRule \
  --ip-protocols UDP \
  --source-addresses "10.2.0.0/16" \
  --destination-addresses "168.63.129.16" \
  --destination-ports 53

# ── Network Rule: allow internal VNet-to-VNet traffic ────────────────────────
az network firewall policy rule-collection-group collection add-filter-collection \
  --resource-group $RG \
  --policy-name $POLICY \
  --rule-collection-group-name "northbank-rules" \
  --name "allow-internal" \
  --collection-priority 300 \
  --action Allow \
  --rule-name "vnet-to-vnet" \
  --rule-type NetworkRule \
  --ip-protocols Any \
  --source-addresses "10.0.0.0/8" \
  --destination-addresses "10.0.0.0/8" \
  --destination-ports "*"

# ── Verify Firewall is logging ────────────────────────────────────────────────
# Enable diagnostic settings to Log Analytics
WORKSPACE_ID=$(az monitor log-analytics workspace show \
  --resource-group $RG \
  --workspace-name logs-northbank \
  --query id --output tsv 2>/dev/null)

az monitor diagnostic-settings create \
  --resource $(az network firewall show --resource-group $RG --name fw-northbank --query id --output tsv) \
  --name "fw-to-loganalytics" \
  --workspace $WORKSPACE_ID \
  --logs '[{"category":"AzureFirewallApplicationRule","enabled":true},{"category":"AzureFirewallNetworkRule","enabled":true}]'

# ── Query Firewall logs (after traffic has been generated) ────────────────────
az monitor log-analytics query \
  --workspace $WORKSPACE_ID \
  --analytics-query "AzureDiagnostics | where Category == 'AzureFirewallNetworkRule' | take 20" \
  --output table
Phase 4

Azure Policy — prevent bad configurations before they happen

RBAC (Session 2) controls who can do things. Azure Policy controls what configurations are allowed — regardless of who is making the change. Even an Owner can't create a public storage account if Policy denies it.

⚖️RBAC vs Azure Policy — the difference

RBAC: "Priya is allowed to create storage accounts" — controls operations

Policy: "No storage account may have public access enabled" — controls resource configuration

They work together. RBAC decides if you can act. Policy decides if what you're trying to create is allowed.

📋Policy effect types
→
Deny — blocks the deployment at creation/update time. Use for hard security requirements.
→
Audit — allows but marks non-compliant. Use for reporting without blocking teams.
→
DeployIfNotExists — auto-deploys a required resource if missing (e.g. auto-enable Defender on new VMs).
→
Modify — auto-adds or changes properties (e.g. add required tags automatically).
Portal

Assign policies from the Azure Portal

Navigate to Azure Policy

Search Policy in the top search bar → click Policy. The Policy dashboard shows compliance overview. Click Definitions in the left menu to see all built-in policies (there are hundreds).

Search: Policy → Policy → Definitions

Find and assign: Require secure transfer for storage accounts

In Definitions, search for Secure transfer. Click Secure transfer to storage accounts should be enabled. Click Assign. Scope: your Resource Group (rg-payments-prod). Effect: Deny. Review + Create.

Definitions → search "Secure transfer" → Assign → Scope: rg-payments-prod → Effect: Deny

Assign: No public blob access on storage accounts

Back in Definitions, search public blob. Find Storage account public access should be disallowed. Assign at Subscription scope this time — this is a company-wide rule. Effect: Deny. Create. Now try to create a storage account with public access — it will be blocked at deployment.

Definitions → "public blob" → Assign → Scope: Subscription → Effect: Deny

Assign: Require tags on all resources (Audit)

Search Require a tag. Find Require a tag on resources. Assign at Subscription. Parameters → Tag Name: CostCenter. Effect: Audit (not Deny — don't break things immediately, audit first). Review + Create.

Definitions → "Require a tag" → Assign → Tag: CostCenter → Effect: Audit

Check compliance — who is failing

Policy → Compliance. Each policy shows % compliant. Click a non-compliant policy to see which specific resources are violating it. This is the audit view — use it in weekly compliance meetings.

Policy → Compliance → click any policy → see non-compliant resources
Terminal — assign built-in policies via CLIbash
SUB_ID=$(az account show --query id --output tsv)
RG="rg-payments-prod"
RG_ID=$(az group show --name $RG --query id --output tsv)

# ── Assign: No public blob access (Deny at Subscription) ─────────────────────
POLICY_DEF=$(az policy definition list \
  --query "[?displayName=='Storage account public access should be disallowed'].name" \
  --output tsv)

az policy assignment create \
  --name "deny-public-storage" \
  --display-name "Northbank: Deny public storage accounts" \
  --policy "$POLICY_DEF" \
  --scope "/subscriptions/$SUB_ID" \
  --params '{"effect":{"value":"Deny"}}'

# ── Assign: Require secure transfer (Deny at RG) ─────────────────────────────
POLICY_DEF2=$(az policy definition list \
  --query "[?displayName=='Secure transfer to storage accounts should be enabled'].name" \
  --output tsv)

az policy assignment create \
  --name "deny-insecure-storage-transfer" \
  --display-name "Northbank: Require HTTPS on storage" \
  --policy "$POLICY_DEF2" \
  --scope "$RG_ID" \
  --params '{"effect":{"value":"Deny"}}'

# ── Assign: Require CostCenter tag (Audit at Subscription) ───────────────────
POLICY_DEF3=$(az policy definition list \
  --query "[?displayName=='Require a tag on resources'].name" \
  --output tsv)

az policy assignment create \
  --name "audit-costcenter-tag" \
  --display-name "Northbank: Audit missing CostCenter tag" \
  --policy "$POLICY_DEF3" \
  --scope "/subscriptions/$SUB_ID" \
  --params '{"tagName":{"value":"CostCenter"},"effect":{"value":"Audit"}}'

# ── List all policy assignments ───────────────────────────────────────────────
az policy assignment list --scope "/subscriptions/$SUB_ID" \
  --query "[].{Name:displayName, Scope:scope}" \
  --output table

# ── Check compliance state ────────────────────────────────────────────────────
az policy state summarize \
  --resource-group $RG \
  --query "results.policyAssignments[].{Policy:policyAssignmentId, Compliant:results.compliantResources, NonCompliant:results.nonCompliantResources}" \
  --output table

When no built-in policy exists, write your own. This example denies VM creation unless it uses a managed disk (no unmanaged disks allowed in Northbank).

Terminal — create and assign a custom Azure Policybash
# ── Write the custom policy definition ───────────────────────────────────────
cat > /tmp/deny-unmanaged-disks.json << 'EOF'
{
  "mode": "All",
  "displayName": "Northbank: Deny VMs without managed disks",
  "description": "Blocks creation of VMs using unmanaged (storage-account-backed) disks",
  "policyRule": {
    "if": {
      "allOf": [
        {
          "field": "type",
          "equals": "Microsoft.Compute/virtualMachines"
        },
        {
          "field": "Microsoft.Compute/virtualMachines/storageProfile.osDisk.vhd",
          "exists": "true"
        }
      ]
    },
    "then": {
      "effect": "[parameters('effect')]"
    }
  },
  "parameters": {
    "effect": {
      "type": "String",
      "defaultValue": "Deny",
      "allowedValues": ["Audit", "Deny", "Disabled"],
      "metadata": {
        "displayName": "Effect",
        "description": "Audit or Deny creation of VMs with unmanaged disks"
      }
    }
  }
}
EOF

# ── Create the custom policy definition ──────────────────────────────────────
az policy definition create \
  --name "northbank-deny-unmanaged-disks" \
  --display-name "Northbank: Deny VMs without managed disks" \
  --description "Blocks VMs using unmanaged disks" \
  --rules /tmp/deny-unmanaged-disks.json \
  --mode All

# ── Assign it at subscription scope ──────────────────────────────────────────
SUB_ID=$(az account show --query id --output tsv)

az policy assignment create \
  --name "northbank-managed-disks-only" \
  --display-name "Northbank: Managed disks only" \
  --policy "northbank-deny-unmanaged-disks" \
  --scope "/subscriptions/$SUB_ID" \
  --params '{"effect":{"value":"Deny"}}'

# ── Test: try to create a VM with unmanaged disk — should be blocked ──────────
az vm create \
  --resource-group rg-payments-prod \
  --name test-blocked-vm \
  --image Ubuntu2204 \
  --use-unmanaged-disk \
  --admin-username azureuser \
  --generate-ssh-keys

Phase 5

NSG Flow Logs + Application Security Groups

Session 1 covered basic NSG rules. Now we go deeper: NSG Flow Logs show you exactly which traffic was allowed or denied (critical for troubleshooting), and Application Security Groups let you write rules using logical names instead of IP addresses.

NSG Flow Logs

See every packet — allowed and denied

Why Flow Logs matter: When a VM can't reach another VM, you don't know if the NSG is blocking it or if the application is refusing the connection. Flow Logs record every flow as Allow/Deny — you can see exactly which NSG rule fired for each connection.

Create a storage account for flow logs

Search Storage accounts → + Create. RG: rg-payments-prod. Name: northbankflowlogs. Performance: Standard. Redundancy: LRS. Public access: Disabled (our Policy from Phase 4 enforces this anyway). Create.

Storage accounts → + Create → northbankflowlogs → LRS → Public: Disabled

Enable Flow Logs on your NSG

Search Network Watcher → left menu Flow logs → + Create. Select your NSG (nsg-payments-app). Storage account: northbankflowlogs. Retention: 30 days. Flow Logs version: Version 2 (includes throughput data). Enable Traffic Analytics: Yes → Log Analytics workspace. Create.

Network Watcher → Flow logs → + Create → nsg-payments-app → storage → Version 2 → Enable Traffic Analytics

Read a Flow Log — understand the format

After 10 min, go to the storage account → Containers → insights-logs-networksecuritygroupflowevent. Navigate the date-partitioned folder to find a JSON file. Each row is a flow tuple: timestamp,src-ip,dst-ip,src-port,dst-port,protocol,direction,action,packets,bytes. A = Allowed, D = Denied.

Storage account → Containers → insights-logs-networksecuritygroupflowevent → date folder → PT1H.json
Terminal — enable NSG flow logs + query denied trafficbash
RG="rg-payments-prod"
NSG_NAME="nsg-payments-app"
LOCATION="westeurope"
STORAGE_NAME="northbankflowlogs"

# ── Create storage account for flow logs ─────────────────────────────────────
az storage account create \
  --name $STORAGE_NAME \
  --resource-group $RG \
  --location $LOCATION \
  --sku Standard_LRS \
  --allow-blob-public-access false

STORAGE_ID=$(az storage account show \
  --name $STORAGE_NAME --resource-group $RG \
  --query id --output tsv)

# ── Enable NSG flow logs (Version 2 includes bytes/packets) ──────────────────
NSG_ID=$(az network nsg show \
  --resource-group $RG --name $NSG_NAME \
  --query id --output tsv)

az network watcher flow-log create \
  --resource-group $RG \
  --name "flow-log-payments-nsg" \
  --nsg $NSG_ID \
  --storage-account $STORAGE_ID \
  --retention 30 \
  --log-version 2 \
  --enabled true \
  --location $LOCATION

# ── Verify flow log is enabled ────────────────────────────────────────────────
az network watcher flow-log show \
  --resource-group $RG \
  --name "flow-log-payments-nsg" \
  --query "{enabled:enabled, retention:retentionPolicy.days, version:format}" \
  --output json

# ── Query Traffic Analytics (requires Log Analytics workspace) ────────────────
# After 30+ minutes of traffic, query denied flows
WORKSPACE_ID=$(az monitor log-analytics workspace show \
  --resource-group $RG --workspace-name logs-northbank \
  --query customerId --output tsv)

# Top denied connections in last 1 hour
az monitor log-analytics query \
  --workspace $WORKSPACE_ID \
  --analytics-query "
    AzureNetworkAnalytics_CL
    | where TimeGenerated > ago(1h)
    | where FlowStatus_s == 'D'
    | summarize DeniedFlows=count() by SrcIP_s, DestIP_s, DestPort_d, L7Protocol_s
    | top 10 by DeniedFlows
  " \
  --output table

Application Security Groups replace IP addresses in NSG rules with logical group names. Instead of "allow 10.2.1.4 to 10.2.1.7", write "allow WebServers to DatabaseServers".

Terminal — Application Security Groups (ASG)bash
RG="rg-payments-prod"

# ── Create ASGs — logical groups for your VMs ─────────────────────────────────
az network asg create --resource-group $RG --name asg-web-servers     --location westeurope
az network asg create --resource-group $RG --name asg-api-servers     --location westeurope
az network asg create --resource-group $RG --name asg-database-servers --location westeurope

# ── Assign VMs' NICs to ASGs ─────────────────────────────────────────────────
# Get NIC name for the VM
NIC_NAME=$(az vm show --resource-group $RG --name payment-api-vm \
  --query "networkProfile.networkInterfaces[0].id" \
  --output tsv | xargs basename)

# Assign NIC to the API servers ASG
az network nic ip-config update \
  --resource-group $RG \
  --nic-name $NIC_NAME \
  --name ipconfig1 \
  --application-security-groups asg-api-servers

# ── Write NSG rules using ASG names instead of IPs ───────────────────────────
NSG="nsg-payments-app"

# Allow: web servers → API servers on port 8080 (no IPs needed!)
az network nsg rule create \
  --resource-group $RG \
  --nsg-name $NSG \
  --name "allow-web-to-api" \
  --priority 100 \
  --direction Inbound \
  --access Allow \
  --protocol Tcp \
  --source-asgs asg-web-servers \
  --destination-asgs asg-api-servers \
  --destination-port-ranges 8080

# Allow: API servers → database servers on port 5432
az network nsg rule create \
  --resource-group $RG \
  --nsg-name $NSG \
  --name "allow-api-to-db" \
  --priority 110 \
  --direction Inbound \
  --access Allow \
  --protocol Tcp \
  --source-asgs asg-api-servers \
  --destination-asgs asg-database-servers \
  --destination-port-ranges 5432

# Deny: web servers → database servers directly (must go via API layer)
az network nsg rule create \
  --resource-group $RG \
  --nsg-name $NSG \
  --name "deny-web-to-db-direct" \
  --priority 120 \
  --direction Inbound \
  --access Deny \
  --protocol Tcp \
  --source-asgs asg-web-servers \
  --destination-asgs asg-database-servers \
  --destination-port-ranges "*"

# When you add a new API server VM, just add its NIC to asg-api-servers
# — it automatically gets all the right NSG rules. No rule edits needed.
